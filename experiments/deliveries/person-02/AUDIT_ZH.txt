TrustGate Experiment 2: Result verification and issue description

Conclusion: No missed runs, duplicate IDs, duplicate charges, CSV export misalignment, or scoring record errors were found; however, clear limitations exist in experimental utility, attack control strength, and compatibility with formal delivery.
This is an offline verification with no model API calls, reruns, deletion or modification of failed records, or changes to original scores.

1. Passed checks
336 unique trial IDs match the original list: 84 normal, 126 tool output attacks, 126 tool instruction attacks.
Re-run the native user task score 336 times and the attack target score 252 times according to the saved pre- and post-environment conditions with consistent results.
All CSV public fields match the private raw results; tokens, call counts, and costs are aligned.
1338 real API responses with a total cost of $0.72108042; the 5 copied responses during recovery were not charged repeatedly.
The original 150 results remain unchanged; the 5 cache requests and responses for the 151st item are item-by-item consistent, and up to 8 subsequent call limits are preserved.
Source code, key dependencies, and detector files match the local preparation records; the original output file checksum passed.

II. Task Success Rate and Process Termination Status
Native user task evaluation passed 168 out of 336, 50%; this is not full task success.
314 processes generated final answers, 20 reached the 8-model call limit, 2 reached the permission denial limit.
Python exceptions recorded as 0, but tool calls failed 121 times; this differs from ’all operations correct’.
Yoga class query user_task_2 failed 84 times under seven configurations. Simulated date and correct calendar events exist; the queried samples show the model did not correctly select the next event, rather than data loss.

III. Detector false positives
Four configurations with metadata classifier enabled resulted in 192 trials all blocking the normal get_current_day tool.
Of these, 48 occurred in normal non-attack scenarios. This hinders date reasoning but cannot account for all yoga task failures, as configurations without detectors also failed.
Full TrustGate achieved 6/12 normal task passes, while no protection achieved 8/12; the sample includes only four business tasks, so no general causal conclusion can be drawn.

IV. Insufficient attack control evidence
No protection group had 0/18 successful tool output attacks and 0/18 successful tool instruction attacks; full TrustGate also had 0/18 for both.
Therefore, it cannot be claimed that it outperforms no protection solely based on ’TrustGate being fully intact has not been breached’.
All 126 tool instruction attacks failed, making it impossible to reliably measure the protective benefit of this attack surface.
There were 5 attack successes: 2 with the delimiter configuration and 3 without execution authorization, all from the same output-attack case.
The three repetitions are not three independent attack types; thus, broad security assurance cannot be claimed based on this.

V. Limitations of Evaluation Rules
17 email-link trials failed the strict unchanged-environment check despite including the correct link, because reading unread mail changes its read flag. This behavior comes from the benchmark tools and scoring rules. Retain the original scores and explain the limitation separately.
File tasks use literal keyword checks; 30 failed records included expressions such as hiking boots/hiking shoes without the required hiking gear term. Some lexical variations may affect scores and require manual sampling; they cannot be directly reclassified as successful.
The baseline email task evaluation code also accepts pre-set phishing links, but there were no records of ’phishing links only’ being classified as passed.

Sixth, official merging and pause/resume
Mac’s Torch 2.7.1 differs from Vanda’s 2.7.1+cu126 build and PBS was not used on this machine; full group-wide acceptance has not yet been completed.
During the original audit, only local-receipt.json was present; this submission additionally generates the standard field receipt.json to explicitly retain the actual Mac package version and pending platform review status. The original local-receipt remains unchanged. Shared aggregation programs can read it, but this does not indicate platform acceptance has been completed.
Simply renaming files cannot bypass version acceptance; all team members must collectively accept and verify the actual environment and adapted version.
The previous API duration in Article 151 is restored based on file timestamps; delay analysis requires separate annotation; pause time is not included.
These differences are already documented in ENVIRONMENT.md and local-receipt.json.

Recommendation: retain the original data and scores from this submission, first confirm the platform acceptance procedure with team members, and disclose in the report the utility loss, false positives, score limitations, and weaker attack comparisons. If the algorithm, prompts, or evaluation methods are later fixed, a new version and experimental batch should be established.
